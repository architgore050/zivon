# Fixtures and goldens

A fixture is an input you control. A golden is an expected artifact or an
invariant set you compare against. A seeded defect is a deliberately broken
input whose expected reviewer verdict is known. All three are production
artefacts of the test suite: they are reviewed, versioned, and never edited to
make a failing test pass.

## 1. Vocabulary

| Term | Meaning here | Example |
|---|---|---|
| **Fixture** | Fixed input staged for a test: JSON, PDF, HTML fragment, PDF page, scripted event stream | `testing/content_factory/mocks/fixtures/03-check.json` |
| **Double / fake** | A test replacement for a collaborator, kept at a seam | `MockBrain` in `testing/voice/mocks/brain.py` |
| **Golden topic** | A published artifact snapshot plus `expected.json` invariants | `evals/goldens/topics/class-9-motion/` |
| **Seeded defect** | A known-bad input with an expected severity/verdict | `evals/goldens/defects/03-check/SD-CHK-001.json` |
| **Recorded artifact** | A read-only output from a real run, used as evidence or input | `runs/<run_id>/<stage>/output.json` |
| **Fixture manifest** | The table that says what a fixture is, where it came from, and how to refresh it | [../templates/fixture-manifest.md](../templates/fixture-manifest.md) |

## 2. Non-negotiable rules

1. **Checked in, deterministic, minimal.** A fixture is a file in git (or a
   tiny builder script), not a download at test time. It must be small enough to
   read in review and stable enough that a rerun is identical.
2. **No network, no secret, no live model.** The test process never reaches a
   vendor. A fixture generated by a live model call is allowed only if it is
   captured once, sanitized, committed, and dated.
3. **No learner data.** No names, emails, phone numbers, school names,
   transcripts, or raw audio. Kid-test fixtures use the DPDP-validated payload
   shape and pseudonymous session codes only. Raw audio is not retained by
   design (ADR-0008); do not add it to a fixture.
4. **Synthetic or licensed.** Fixture PDFs are hand-built (`make_pdfs.py`) or
   public-domain/NCERT-derived with provenance. Never a scraped copyrighted
   textbook.
5. **Output goes to a temp directory.** Copy a fixture into
   `tempfile.TemporaryDirectory()` before mutating it; never write a tracked
   file from a test.
6. **Clean up.** Temp dirs, HTTP servers, browser contexts, DB connections, and
   subprocesses all close in `addCleanup`, `finally`, or a context manager.
7. **Name by purpose, not by sequence.** `03-check__fail400.json` says what it
   does; `fixture2.json` does not.
8. **A golden records invariants, not one exact wording.** Model output varies
   legitimately. Assert structure, counts, required concepts, numerical
   anchors, and safety properties — not the sentence the model happened to
   produce.

## 4. Creating a fixture

1. **Write the smallest input that exercises the behaviour.** For a stage
   fixture, use the real handoff shape (schema-valid), not an ad-hoc dict.
2. **Pin the source.** Add a row to the fixture manifest (or the README table)
   naming the origin: hand-written, captured from a run id, derived from a
   public-domain document, or generated by a deterministic script.
3. **Date it.** A fixture captured from a live run records the date, the
   pipeline version, and the stage. Perishable shapes rot.
4. **Validate it.** If the fixture claims to be schema-valid, load it in a test
   through the real schema validator (`testing/content_factory/unit/test_schemas.py`
   does this for the committed fixtures). A fixture that no longer validates is
   either stale or the schema changed; decide which, deliberately.
5. **Stage it, don't touch it.** Copy into a temp dir for any test that writes.

```python
import shutil
import tempfile
import unittest
from pathlib import Path

FIXTURES = Path(__file__).resolve().parent / "fixtures"


class StageFixtureTest(unittest.TestCase):
    def setUp(self) -> None:
        self.tmp = tempfile.TemporaryDirectory()
        self.addCleanup(self.tmp.cleanup)
        self.work = Path(self.tmp.name)
        shutil.copy2(FIXTURES / "03-check.json", self.work / "03-check.json")

    def test_fixture_is_staged_outside_the_repo(self) -> None:
        self.assertTrue((self.work / "03-check.json").is_file())
        self.assertFalse(
            (FIXTURES / "03-check.json").samefile(self.work / "03-check.json")
        )
```

## 5. Golden topics

A golden topic is a published page plus the properties it must keep. It is not
a screenshot and not a sentence-for-sentence expected output.

**Layout** (`evals/goldens/topics/class-9-motion/`):

| File | Contains |
|---|---|
| `artifact_ref.json` | Where the snapshot came from: run id, published path, pipeline version, hash/date |
| `expected.json` | Invariants: schema bounds, required concepts/equations, numerical anchors with tolerance, forbidden smuggled terms, visual/kit invariants, perf budgets |
| `source_pack_meta.json` | The source provenance the page must stay grounded in |

**Rules:**

- **Register every golden** in `evals/goldens/manifest.json`
  (`golden_topics` and `seeded_defect_sets`). An unregistered golden is not
  seen by the runner.
- **Assert properties, not phrasing.** `expected.json` carries counts and
  ranges (`blocks_min/max`, `checks_min`), required terms, equation patterns,
  numerical anchors with a relative tolerance, and forbidden concepts. This is
  what makes a generative output testable without brittle string snapshots.
- **Rotate deliberately.** Use
  `python -m evals rotate-golden --topic-id <slug> --reason "<why>"`; keep the
  previous snapshot in git history; never silently mutate `expected.json` or a
  golden artifact. A deliberate baseline change is stated in the PR with the
  new expected values.
- **A golden is not a fixture you invent.** Use a real published artifact or a
  recorded run; do not hand-write a fake page and call it a golden. If no real
  artifact exists yet, write a unit fixture for the contract and leave the
  golden for when the first real page lands.

## 6. Seeded defects

The 19 seeded defects calibrate reviewers. Each JSON file carries
`sample_id`, `stage`, `origin_incident`, `defect_class`, `planted_mutation`,
`target_call`, `inputs`, and `expected` (the verdict/issue set).

- **Do not edit a defect to make a reviewer pass.** That destroys the
  calibration baseline. If the reviewer is wrong, fix the reviewer and record
  the calibration run; if the defect is genuinely ambiguous, record the
  decision and add a new sample rather than mutating the old one.
- **A new defect needs an origin.** Capture the real incident or construct a
  class the reviewer must catch, then add it to the manifest set and the
  calibration mapping.
- **Run calibration in the infra window** when it needs a live judge:
  `python -m evals calibrate --stage all --mock` first, then live with founder
  approval. See [evals-vs-tests.md](evals-vs-tests.md).

## 7. Recorded artifacts

- `runs/<run_id>/` is evidence, not a fixture library. Read it; do not write it
  from a test. The cluster keeps it on the `zivon-sources` PVC; the host copy is
  gitignored.
- `frontend/courses/` is the published snapshot. Tests may read it; only the
  publish flow writes it.
- When a recorded artifact becomes a regression input, promote a **minimal,
  sanitized** slice into `testing/.../fixtures/` and record its origin in the
  manifest. Do not point a unit test at a mutable `runs/` path.

## 8. PII, DPDP, and privacy

- Fixtures are synthetic. A transcript fixture is a hand-written code-mixed
  sentence, not a real student's audio transcript.
- Kid-session records use the `record-kid-test` payload: pseudonymous session
  code, class/topic class, boolean comprehension signals, consent record id. No
  names, emails, phones, schools, or free-form identifying notes.
- Never put raw audio, prompts, completions, or page HTML in a log fixture. If a
  test needs the shape, use a redacted placeholder and assert the redaction
  contract (`testing/observability/test_redaction.py`).
- A fixture that accidentally contains a real email or phone number is a review
  blocker; the skill validator and gitleaks catch patterns, not intent.

## 9. Cleanup checklist

- [ ] Mutated inputs were copied to a temp dir; tracked files are unchanged.
- [ ] Temp directories use `TemporaryDirectory` / `addCleanup`.
- [ ] HTTP servers (`serve_static`) shut down in `finally`.
- [ ] Browser contexts and pages close; no orphan Chromium process.
- [ ] Subprocesses terminate; the orchestrator's own deadline is respected.
- [ ] Database rows are in an in-memory or temp DB; no shared Postgres state.
- [ ] The test passes when run alone and in a shuffled/repeated order.

## 10. Anti-patterns

| Pattern | Why it fails |
|---|---|
| Giant inline JSON in the test body | Unreviewable, duplicated, and rots silently |
| Fixture generated by the code under test | Tautology: the test compares the code to itself |
| Fixture copied from a real student session | Privacy violation; DPDP exposure |
| Golden with exact prose | Fails on legitimate paraphrase; trains reviewers to rubber-stamp |
| Editing a seeded defect to pass | Destroys calibration; hides a reviewer regression |
| Writing into `runs/` or `frontend/` from a test | Pollutes evidence and the published snapshot |
| Sharing one temp path across tests | Order dependence and flaky cleanup |
| Untracked fixture downloaded at runtime | Non-hermetic; CI becomes network-dependent |
| A fixture with no provenance row | Nobody can tell whether it is still valid |
