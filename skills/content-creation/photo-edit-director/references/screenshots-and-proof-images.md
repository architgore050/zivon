# Screenshots as proof

A screenshot is credible when it shows one real thing clearly. It fails when it shows a whole screen.

## Capture
- Largest window you can, then crop in the edit. Dark or light theme chosen once and kept across the set.
- Terminals and editors: font 16 pt+; browsers: zoom 125-150 percent.
- Hide: notifications, tabs, bookmarks, profile photos and emails, tokens, .env content, internal URLs.

## Crop and focus
- Crop to the 10-20 percent of the screen that matters. Keep just enough surrounding context to be believable
  (a file name, a header, a timestamp).
- Show the number or output, not the tool. The viewer cares about the result.
- If a before/after pair helps, give both the same crop and scale.

## Annotation (at most one per image)
- A single box, arrow, or highlight in one accent colour. No arrows pointing at arrows.
- Highlight what the caption/post talks about, nothing else.
- Callout text under 7 words, in the post's typeface family.

## Redaction
- Solid opaque rectangles in the background colour or a neutral grey. Not blur, not low-opacity overlays, not
  mosaic. Check that redacted text is not still in a layer or in metadata when exporting (flatten, then re-inspect
  the exported file).
- Strip EXIF/metadata from photos before posting (location, device).
- Re-view the exported file, not the working file.

## Doc/timeline screenshots (done vs not done)
- Make the not-done items visible; honesty is the credibility signal in day-N posts.
- If the plan has sensitive details, create a clean summary card instead (3-5 lines, same typography).

## Card graphics (text on background)
- One decision or one number per card. Big type, high contrast, one accent colour, a lot of empty space.
- A decision card format: "Decision: [what]. Tradeoff: [what it costs]. Why: [one line]."

## Integrity
- Never edit values, names, or UI states in a screenshot. If a state is hard to reproduce, recapture it.
- If an image is a mockup rather than the real product, label it as a mockup.
